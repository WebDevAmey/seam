# Limitations

Disclosed, quantified where possible, not explained away. Each of these is a real gap in the current build, not a hedge.

## 1. One leak class has no detector

`POST_PURCHASE_LEAK` (needs a refund/return data model that doesn't exist in this schema yet) is named in the taxonomy but not implemented. `classifyCheckout` classifies the other four leak classes directly; `METHOD_CONCENTRATION` is detected separately, on demand, by `src/intelligence/analyze-merchant.ts` (a z-score comparison of today's per-method failure rate against a 7-day rolling baseline, requiring `MIN_BASELINE_DAYS = 7` and `MIN_SAMPLE_SIZE = 5` before it will flag anything) rather than folded into the real-time sweep — it's a structural, merchant-wide signal, not a per-checkout one, so it runs as its own endpoint (`POST /merchants/:id/intelligence/analyze`) instead of on every webhook. Quantified: 1 of 6 leak classes, 0% coverage.

## 2. "Net rupees recovered" is predicted EV, not realised recovery

There's no outcome worker in this build — nothing listens for a `payment.captured` webhook arriving within 72h of a dispatched action and attributes it back. So every recovery number in `EVALUATION.md` is the policy's own expected-value arithmetic, using hand-set (not learned, not validated against real outcomes) priors in `src/policy/decide.ts`. The eval proves the arithmetic is internally consistent and the gating logic works; it does not prove real rupees moved, because none did — this is entirely test-mode/synthetic data.

## 3. On the eval data run so far, Seam ties or trails `blast_everything` on auto-dispatched net value

Full explanation, not just the number, is in `EVALUATION.md`. Short version: across both the dev and held-out seeded sets, every gap between Seam's net and the naive "message everyone" baseline is fully explained by Shield correctly holding specific actions back — one for human approval, one below the profitability floor — that the naive strategy would have fired blindly. Seam's *total addressable value* (dispatched + pending approval) is within ~0.3% of blast_everything's on the held-out run. The eval, as currently built, generates independent single-day leaks with no repeat customers, so it never gives Shield's contact-cap the chance to matter — that's a real gap in eval *scenario coverage*, disclosed rather than hidden, and it means the "beats blast_everything on net" claim is not yet cleanly proven at the portfolio level, even though the underlying floor and cap logic are individually tested and correct in isolation.

## 4. The LLM diagnosis path — now exercised against a real live model, with real results

Real credentials now exist (`GROQ_API_KEY`, `src/llm/providers.ts`'s `diagnosisModel()` → Groq's `openai/gpt-oss-20b`), so this is no longer a disclosed gap in the old sense: `classify-with-openai.live.test.ts` runs every one of the 7 prompt-injection fixtures (plus a plain, non-adversarial decline) against the real model and checks the *actual* classification, not just the downstream safety-path handling that `graph.test.ts` already proved against a mock. As of this build, the real model gets all 8 right.

That's a genuine result worth being precise about the scope of: 8 fixtures is not a statistically powered claim about detection quality in general, and there's still no Langfuse account or larger eval set behind it. What it does prove is that the specific defense prompt in `classify-with-openai.ts`, against this specific model, correctly separates every attack fixture from every benign one in this build's own test set — a stronger claim than "fully written but never run," which is what this section used to say.

Model choice was a real, measured tradeoff, not a default: Groq deprecated the `llama-3.3-70b` line since this build's LLM plumbing was first written (`groqClient.chat("llama-3.3-70b-versatile")` 404s — that model id no longer exists on Groq). `openai/gpt-oss-120b` classifies correctly too, but under this test suite's own concurrent load it occasionally exceeded the diagnosis path's 4s per-round timeout (PRD §8); `openai/gpt-oss-20b` is both fast enough to stay comfortably inside that budget (under ~1.5s per call, observed) and, on this fixture set, no less accurate. The live test also carries `retry: 2` on each case — not to paper over a real detection failure, but because a single call occasionally queues past 4s under the test file's own parallel load, which is exactly the transient failure mode `graph.ts`'s own `MAX_ROUNDS = 2` is already built to absorb in production; the live test now mirrors that same resilience instead of being flakier than the system it's testing.

## 5. No real WhatsApp (or SMS) adapter, outbound or inbound

Outbound: both channels are simulated behind a `ChannelAdapter` interface shaped so a real implementation is a one-file swap. Neither sends a real message anywhere. This was originally planned around reusing a real Business Cloud API adapter from elsewhere; that source is no longer available to this standalone build (see `LEARNINGS.md`). Inbound: there's no real webhook receiving customer replies either — `POST /recovery-actions/:id/reply` stands in for "a reply arrived," so a real integration would swap the transport at that one boundary, but everything downstream of it (`classifyReply`, `Ticket` creation, the `OptOut` write Shield actually reads) is real, not stubbed.

## 6. Real login/session auth exists — `apps/api`'s merchant-scoped routes now verify it too

`apps/web` has real signup/login/logout — JWT-in-httpOnly-cookie, bcrypt-hashed passwords, middleware-gated routes, adapted from `causal-ai`'s own auth pattern (see `DECISIONS.md`). Every `/merchants/:id/...` route on `apps/api` (`leaks`, `recovery-actions`, `digest`, `tickets`, `intelligence/analyze`, `razorpay/connect`) is now behind `src/auth/middleware.ts`: a request needs a valid `Authorization: Bearer <token>`, and the session's own `merchantId` has to match the `:id` in the URL — a valid session for merchant A gets a 403 requesting merchant B's data, not a 200. `apps/web`'s server-side fetches (`lib/api.ts`) forward the same httpOnly cookie's token automatically, so nothing changed for the UI. Proven with real HTTP tests (`*/routes.test.ts`), not just unit tests of the underlying functions: 401 with no token, 403 with someone else's, 200 with your own.

Two things stay deliberately outside this boundary. `/webhooks/*` are authenticated differently (HMAC signatures from Razorpay/Shopify, not a merchant session — that's the correct mechanism for a server-to-server webhook, not a gap). `GET /ledger` and `GET /ledger/verify` stay unauthenticated by design: the hash chain is one global, publicly verifiable structure by construction (`ARCHITECTURE.md`), and the PRD's own submission video calls for verifying it live, so requiring login to check the ledger's integrity would work against the point of it being independently verifiable.

There is also no email verification and no password-reset flow — Seam has no email-sending credentials configured (same category of gap as §4/§5). An account is active immediately after signup.

## 7. Diagnosis accuracy against ground truth isn't measured

The generator plants a leak *class* but not an independent "true underlying decline reason" label separate from what it writes onto the `PaymentAttempt` row itself, so there's no independent ground truth to score `classifyDiagnosis` against without the eval trivially grading its own homework. Combined with §4 above (no live LLM), this metric from the original evaluation plan isn't reported.

## 8. One shared Postgres connection pool

`apps/api`'s `prisma.ts` is a single `PrismaClient` instance backing every route — ingest, resolve, detect, execute, the read APIs the frontend calls. A slow or wide query anywhere can compete for connections with a latency-sensitive webhook ack. Not yet split into dedicated pools per subsystem; disclosed as a known architectural simplification, not discovered live.

## 9. Deployment hasn't happened yet

Render, Neon, and the GitHub Actions keep-warm cron are all planned (`PRD.md` §3.3) but not yet set up — everything in this build has been run and tested locally. The cold-start risk that plan discloses is real once deployed; right now it's simply not deployed. The auth gap that used to be listed here as a pre-deploy blocker (§6) is closed as of this build.

## 10. Detect → diagnose → decide → Shield → reserve now runs live — dispatch is still the one step it stops short of

This used to say nothing in the running app wired `classifyDiagnosis` → `decide` → `evaluateShield` together against a merchant's real leaks — that chain only ever ran inside eval scripts, against synthetic data. It's closed now, for real: `src/agents/diagnosis-agent.ts` persists a real `Diagnosis` row per undiagnosed leak (rules first, escalating to the live LLM — Groq, per §4 — when rules can't resolve it; previously nothing in this codebase ever wrote to the `Diagnosis` table at all, so the fleet's "diagnoses run" count had always silently read 0), and `src/agents/recovery-executor.ts` runs `decide()` + `evaluateShield()` over every unaddressed leak and actually calls `reserveAction()` — a real `RecoveryAction` row, `RESERVED` if Shield passes it or `FAILED` with the real reason if Shield blocks it. Both are live-triggerable (`POST /merchants/:id/agents/{diagnosis,recovery}/run`), harnessed the same way as every other agent, and a fleet-page **"Run all agents"** button runs the whole sweep — detector, diagnosis, recovery, shield, intelligence, opportunities, in that dependency order — in one click.

What still doesn't happen: the executor never calls `executeAction`. A real dispatch needs a merchant's actual, connected, decrypted Razorpay test-mode credentials (`RazorpayConnection`), and nothing in this build — including the seeded demo merchant — has one configured (same underlying gap named in §13). Every `RESERVED` action the executor creates is exactly what the recovery queue's approve/reject flow (§13) is for: a human decision on a real, computed proposal, not a simulated one.

A **Shield recheck** agent (`src/agents/shield-recheck.ts`, `POST /merchants/:id/agents/shield/run`) closes the "protect" half similarly, but with an honest, narrower scope than Shield's full seven-check surface: it re-verifies the quiet-hours and EV-floor checks (the two that only need the current time and the leak's own stored amount) over every currently-`RESERVED` action, using currently-live data — a real check for real drift (an action reserved at 3pm that's now inside quiet hours, say). Opt-out status and the 7-day contact count default to their most permissive values rather than being faked as "still checked," because `RecoveryAction` doesn't retain a customer contact to look either up by (the same schema gap §13 names) — it's a recheck, not a full re-run, and is disclosed as one rather than silently narrowed.

## 11. The "agent fleet" is a naming and organisation layer over existing code, not new autonomous behaviour

`src/agents/registry.ts` names and describes eight automated workers already built elsewhere in this codebase (detector, diagnosis, policy, shield, executor, leak intelligence, reply classifier, digest) plus the two genuinely new pieces (§10's Opportunities Agent, §12's chat agent) — it's a real, honest inventory (`GET /merchants/:id/agents`, `/recovery/agents`), not a rebrand that claims new capability the code doesn't have. Seven of the nine are marked `deterministic` in that registry and are exactly that — plain code, no model call, ever. Diagnosis and the chat agent are marked `llm-assisted`; per §4, Diagnosis now runs against a real live Groq model, and per §12, chat needs `OPENROUTER_API_KEY` set to run at all.

Every agent invocation now goes through a real harness (`src/agents/harness.ts`'s `recordAgentRun`), writing an `AgentRun` row with status, a one-line summary, full input/output (or the real error, on failure), and a duration — inspectable per-agent at `/recovery/agents/:agentId`, each run expandable to its actual payload rather than a simulated activity count. This is real, tested (`harness.test.ts`), and wired into every agent that has a live route. The fleet page and each agent's detail page also show a real success-rate bar (`okRunCount`/`runCount`, §15) wherever an agent has actually been run.

## 12. The "chat with your store" agent needs `OPENROUTER_API_KEY` to do anything, and is deliberately read-only

`src/agents/chat/` is a genuinely new LLM-assisted agent — not a rebrand of existing code — that answers natural-language questions about a merchant's own data by calling four tools (`getRevenueLeakSummary`, `getTopOpportunities`, `getOpenConversations`, `checkLedgerIntegrity`), each a thin wrapper around a function that's already real and already tested elsewhere. `POST /merchants/:id/chat` 503s with an explicit message when no key is configured, rather than silently failing or fabricating a reply. A real `OPENROUTER_API_KEY` is now set for this build (`chatModel()` in `src/llm/providers.ts` → OpenRouter's `openai/gpt-4o-mini`), so this path runs live, not just against a mock — verified against the real running dev server (`curl -X POST /merchants/:id/chat`), not only in the test suite.

Deliberately scoped: the tools exposed to the model are all read-only. There is no send-message, dispatch-recovery, or write-anything tool available to it — the chat agent can tell a founder what Seam's other agents found or would do, but cannot itself cause an action none of those agents could already take on their own. That's a scope choice (avoid an LLM taking a consequential action from natural-language input), not a technical limitation — extending it to a confirmable "yes, send that" flow would be a deliberate, disclosed decision to make later, not an accidental gap.

Testing follows the same honest split as everywhere else in this build: `run-chat.test.ts` proves the real orchestration (thread persistence, multi-turn history, genuine tool execution) against a scripted mock model, and `run-chat.live.test.ts` is a real, live call to OpenRouter that auto-skips when there's no key rather than needing a manual step to exercise.

## 13. "Approve" on a recovery action checks Razorpay connection status and stops there — it never dispatches

`POST /recovery-actions/:id/approve` (`src/execute/review-action.ts`) loads the pending action, confirms it belongs to the calling merchant and is still `RESERVED`, then checks whether that merchant has a `CONNECTED` `RazorpayConnection`. If not — true for every merchant in this build, including the seeded demo — it returns `{ outcome: "not_connected" }` (409) and the frontend (`/recovery/queue`'s `ApprovalItem`) shows that reason plainly rather than a fake success state. If a connection did exist, the route still throws `"approving a connected merchant's action isn't implemented yet"`, because `RecoveryAction` doesn't retain what a real dispatch needs (`amountPaise`, a customer contact) — reconstructing those would mean widening the schema, not just writing the dispatch call.

**Reject is the opposite: fully real, not scoped down.** `POST /recovery-actions/:id/reject` moves the action to `FAILED` and appends a real ledger entry (`action_rejected`, with the reason) — there was no missing data blocking it, so it isn't stubbed. The asymmetry is deliberate: build the real thing wherever the data supports it, and return an honest, specific reason wherever it doesn't, rather than faking either outcome. 5 tests in `review-action.test.ts` cover both paths, including that a rejected/approved action can't be approved or rejected again (state must be `RESERVED`) and that a cross-merchant `recoveryActionId` is treated as not found, not as someone else's data.

## 14. The Groq/OpenRouter switch surfaced (and fixed) a real upstream schema bug — worth naming so it isn't mistaken for a workaround

`generateObject`'s default path (a zod schema, auto-converted to JSON Schema) sends a schema to Groq's strict `response_format: json_schema` mode that includes a zod-v4-internal `~standard` key — not valid JSON Schema. Groq's own validator correctly rejects it, and the model, trying to satisfy an impossible-looking schema, sometimes echoed schema-shaped keys (`$schema`, `properties`, `required`) back inside its own answer object instead of just answering. `classify-with-openai.ts` now hand-writes the JSON Schema via `ai`'s `jsonSchema()` helper (which skips the zod-to-JSON-Schema conversion entirely), with `diagnosisOutputSchema.safeParse` still doing the real runtime validation via `jsonSchema()`'s `validate` callback — the actual data contract didn't loosen, only how it reaches Groq. This is a version-compatibility bug between `ai@7.0.92`/`@ai-sdk/openai@4.0.58` and `zod@4.4.3`, not a defect in Groq's models or in this codebase's own schema design, and it would resurface for any future `generateObject` call against Groq (or any other provider using the same strict-schema code path) unless a future `@ai-sdk/openai` release fixes the underlying conversion.

## 15. The agent fleet's "% ok" success-rate bar reflects `AgentRun` history only, not a broader SLA

`/merchants/:id/agents` now returns `okRunCount` alongside `runCount` (a real `groupBy` over `AgentRun.status`), rendered as a real, data-bound bar (`components/ui/ratio-bar.tsx`) on the fleet cards and the agent detail page — not beUI's `Loader` "percent" variant, which animates its own fake 0→100 loop on a timer and has no prop for a real value, so it was deliberately not used for this. The rate is only as meaningful as how often an agent has actually been run: an agent with 1 recorded run shows 0% or 100%, not a stable average, and agents that have never been triggered (most of the deterministic ones, outside a manual "Run now" or the seed script) show no bar at all rather than a misleading 0%.

## 16. The seed script's demo dataset is engineered for reliable demoability, disclosed rather than left implicit

`scripts/seed-demo.ts` runs the real pipeline end to end (§10) over generated data, but two specific leaks are hand-inserted rather than left to the generator's own randomness: one with a decline reason (`payment_failed`) deliberately outside `classifyDiagnosis`'s rules, so the Diagnosis Agent's live LLM escalation is guaranteed to fire at least once every time the script runs, and one sized so it clears `decide()`'s own EV floor but falls under Shield's separate ₹200 amount floor, so there's always at least one real, visible blocked action to demonstrate Shield actually blocking something. Without these, whether either path fires at all would depend on the generator's random draws for that particular seed run. Both are disclosed in the script's own comments, and both still go through the identical real `classifyDiagnosis` → `decide()` → `evaluateShield()` → `reserveAction()` code path as every generated leak — nothing about their outcome is hand-computed or faked, only their existence is guaranteed rather than left to chance.

The executor and Shield-recheck agents also run against a clock pinned to a fixed daytime IST hour on today's real date, not the actual moment the script happens to run — Shield's quiet-hours check (21:00-09:00 IST) is real and correctly fail-closed, and a seed run that happened to execute at 2am IST would otherwise block every dispatchable action, leaving nothing in the "awaiting approval" state to demo the approve/reject flow against. A live "Run now" / "Run all agents" click from the actual running app always uses the real current time, quiet hours included — this pinning is specific to what the seed script produces, not a change to how Shield evaluates a live request.

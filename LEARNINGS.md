# Learnings

An honest, running account of building Seam: the real problem we set out to solve, what we decided and why, what broke, and how we fixed it. Written as we go — not reconstructed afterward to look tidier than it was.

---

## The problem

A D2C merchant's revenue moves through one funnel: someone browses, adds to cart, starts checkout, attempts to pay, and — if everything goes right — the order gets fulfilled. That funnel is watched by two systems that share no customer identity with each other. The storefront platform (Shopify) sees the shopping behavior. The payment gateway (Razorpay) sees the money moving. Neither one sees both halves.

So when a founder asks the only question they actually care about — *"revenue dropped ₹2L yesterday, why?"* — both systems give a half-answer:

- The storefront says checkout abandonment spiked 40%. It has no idea those customers actually tried to pay and were declined.
- The gateway says `payment.failed` fired 214 times. It has no idea those were ₹12,000 carts from repeat customers who all came from one ad campaign.

Every "recover my failed payments" tool we could find starts at the payment event — the one half the gateway can see. That makes them all blind to the larger, more common category of leak: money lost *before* a payment is ever attempted (a shipping-cost surprise at checkout, a broken step, a slow page) or lost *after* it succeeds (refunds, returns). Treating "revenue leak" as a synonym for "payment failure" is exactly why merchants keep fixing the visible, cheap problem and missing the expensive, invisible one.

## Our approach

Join the two systems at the one place they can actually be joined — the checkout — by carrying a Shopify checkout ID through Razorpay's `notes` field into the payment record, with a scored fallback (email, phone, amount, timestamp) for stores that haven't wired the deterministic join. Once joined, classify every rupee of leak into one of a fixed set of causes, compute whether recovering it is worth the cost of trying — expected value, not gut feel — and only act on the leaks that clear that bar, through a deterministic gate a language model can never talk its way around.

Full spec lives in the private planning doc (not in this repo); this file is the log of what actually happened building it.

## Build log

### Project setup — fresh standalone repo
**What:** stood up `apps/api` (Hono + TypeScript + Prisma 7 + Postgres) as its own pnpm workspace, with nothing shared with any other codebase.
**Why:** a clean, fully-owned build we can reason about end to end, rather than a fork of something else's history.
**Tradeoff:** no inherited auth, OAuth, or UI shell to lean on — everything gets built from scratch, on purpose.

### Bug — Prisma client silently stale after a schema change
**What broke:** added a `processedAt` column to `RawEvent`, ran `prisma db push`, and the generated client still didn't know the field existed — every query using it failed with "Unknown argument."
**Why:** `db push` syncs the database but doesn't reliably regenerate the TypeScript client on its own.
**Fix:** run `prisma generate` explicitly after every schema change. The `db:push` script now always chains `prisma db push && prisma generate` so this can't be forgotten again.

### Bug — a "tampered ciphertext" test that wasn't actually testing tampering
**What broke:** a test asserting that decrypting a tampered AES-256-GCM ciphertext throws — it didn't throw, and the encryption looked broken.
**Why:** the test tampered by appending a character to the base64-encoded ciphertext. Base64 decoding is lenient about trailing characters, so the "tampered" string decoded back to the *same* bytes as the original — the encryption was fine, the test was wrong.
**Fix:** tamper at the byte level (flip one bit in the decoded buffer, then re-encode) instead of the text level. Worth remembering generally: string-level mutation of an encoded value doesn't reliably mutate the underlying bytes.
**Learning:** a failing assertion isn't proof the implementation is wrong — the checkpointer test suite caught this because we wrote the test *before* assuming what "tampered" should look like.

### Bug — hit an unrelated local service instead of our own
**What broke:** an early smoke test curled `localhost:8080/health` and got back an Apache Tomcat 404 page instead of our own server's response.
**Why:** two compounding mistakes — the shell had no `timeout` binary (not present on macOS by default, so a `timeout 6 ... &` command silently failed to even start our server), and port 8080 was already occupied locally by an unrelated Java/Tomcat process.
**Fix:** moved the dev server to port 8090, and switched to running background processes through a tracked mechanism instead of a bare `&` subshell so failures are visible instead of silent.

### Learning — LangGraph.js's Postgres checkpointer needed proving, not assuming
Before writing any pipeline code, we tested whether LangGraph.js's Postgres-backed checkpointer actually gives crash-resumable runs against the *same* database our own ORM manages. It does — and it keeps its own tables in a separate Postgres schema by explicit configuration, so there's zero collision risk with our application tables. Confirmed with a real test: a two-node graph, a simulated crash after the first node completes, and a fresh graph instance (standing in for a new process) that resumes and completes without re-running the first node. Proven before it became load-bearing, not assumed.

### Learning — Razorpay has no merchant-facing OAuth
Shopify apps get a real OAuth redirect flow; Razorpay does not offer the equivalent for ordinary merchants — its OAuth product requires partner approval. The realistic pattern (and what real Razorpay integrations actually do in test mode) is the merchant pasting their Key ID and Key Secret directly. We verify those are real by making one authenticated call to Razorpay's API before ever encrypting and storing them — so a typo or a revoked key is caught at connect time, not the first time a webhook needs it.

### Bug — a test that passed alone and failed as part of the full suite
**What broke:** the Shopify webhook tests passed running on their own, then failed with "expected undefined" when run alongside every other test.
**Why:** the test payloads used fixed order ids (1001, 1002, ...) to build the dedup key (`source` + `externalId`). That key is unique across the *whole* database, and the local dev Postgres instance persists between test runs — so a second run's "new" order 1001 collided with the row a previous run had already inserted for a different merchant. Prisma's `upsert` quietly took the "already exists, no-op" branch instead of creating a fresh row, so the new test's merchant never got its event.
**Fix:** generate a fresh random id per test run instead of a fixed literal, matching the pattern the Razorpay webhook tests already used.
**Learning:** a fixed literal in a test is only safe if the database gets reset between runs. Ours doesn't (real Postgres, not a fresh sandbox per test), so every test that writes rows needs to generate its own unique inputs — and "passes in isolation" is not the same guarantee as "passes as part of the suite."

### Bug — a flaky test caused by a *correct* design decision
**What broke:** the queue-claim concurrency test (6 workers racing over 12 rows) started intermittently claiming only 2 of its 12 rows once a second test file (`/internal/sweep`) also started claiming from the same table.
**Why:** `claimUnprocessedRawEvents` claims globally across every merchant — correct for production, since a sweep has to drain *all* pending work, not just one merchant's. But vitest runs test files in parallel by default, so two files both pulling from the same real, shared queue table started competing for each other's rows.
**Fix:** turned off file-level parallelism in `vitest.config.ts` rather than artificially scoping the claim query to make tests convenient — the query being global is correct; the tests running concurrently against a shared real table was the actual problem. Confirmed with three back-to-back full-suite runs, not one lucky pass.

### Decision — the join scorer is a pure function, deliberately decoupled from the database
**What:** `resolveJoin(payment, candidates)` takes plain objects in, returns a plain result out — no Prisma import, no I/O.
**Why:** this is the actual differentiator (most competing approaches never join the two data sources at all), so it needs to be provably correct on its own, independent of how candidates get fetched. All 9 tests run in milliseconds with no database.
**Learning:** floating-point addition needed a rounding guard (`0.40 + 0.35` can print as `0.7499999999999999` in JS) — rounding to 2 decimal places after summing avoids a boundary case (exactly 0.75) silently landing on the wrong side of the accept/ambiguous line.

### Bug — a generator that used real wall-clock time instead of a fixed anchor, breaking its own determinism
**What broke:** `METHOD_CONCENTRATION`'s eval test failed consistently across several reruns, but a standalone debug script reproducing the exact same seed and parameters found the concentration spike just fine — the same inputs producing different outputs depending on which script ran them.
**Why:** `generatePaymentHistory` anchored its 14-day window on `new Date()` — real wall-clock time — instead of a fixed reference date. Every call at a different real moment shifted which calendar day was "today," breaking the "same seed → same result" guarantee every other generator in this codebase already honors (`generate-merchant-day.ts` takes an explicit `date` parameter for exactly this reason). A second, compounding bug: a random 0–20 hour offset added to a 10:00 UTC base could push an attempt's timestamp past midnight into the next calendar day, silently corrupting which day's bucket it landed in.
**Fix:** a fixed default anchor date (overridable, but deterministic by default), and every attempt's timestamp now stays strictly inside its own day's 00:00–23:59 UTC window.
**Learning:** "it fails in the test suite but works in my one-off debug script" is itself a symptom worth taking seriously — it means something external to the code under test (here, wall-clock time) is a hidden input. Found by actually comparing the two runs' outputs side by side rather than guessing at another parameter to tune.

### Decision — real auth, adapted from `causal-ai`'s pattern rather than reinvented, split across the app boundary Seam already has
Full reasoning in `DECISIONS.md`. Short version: the JWT/bcrypt/middleware *pattern* is generic and worth reusing on its own technical merits; the *code* couldn't move over unmodified because `causal-ai` calls Prisma directly from Next.js and Seam's `apps/web` deliberately never touches the database (see the earlier CORS-avoidance decision). Signing lives in `apps/api` (where the database already is); verifying is a fast, local, no-round-trip check in `apps/web`'s middleware, using a JWT secret shared between the two `.env` files. This also directly closes the auth gap `LIMITATIONS.md` had been carrying since Block 8 — the three screens now render whichever merchant is actually logged in, not a hardcoded demo ID.

### Bug — two stale background dev servers survived their own `TaskStop`, and cost real time to notice
**What broke:** after finishing the auth build, both `apps/api` and `apps/web` failed to boot with `EADDRINUSE` — something was already listening on both ports.
**Why:** earlier dev-server processes from the same session were still running despite having been "stopped" — one turned out to be a genuinely orphaned process on port 8090, and the other was Next.js's own single-instance lock file protecting a dev server on port 3000 that predated all of this turn's route restructuring (the new `middleware.ts`, the `(app)`/`(auth)` route groups) — so even after finding it, it needed killing and a fresh start rather than reuse, since Next.js doesn't hot-reload structural changes like a newly-added middleware file.
**Fix:** `lsof -iTCP:<port> -sTCP:LISTEN` to find the actual PID, `kill` it directly, then start clean.
**Learning:** stopping a tracked background task doesn't guarantee the underlying process is gone, and an old dev server sitting on a port isn't just noise — it can be silently serving pre-change code and produce confusing 500s that look like new bugs. Worth checking `lsof` directly rather than assuming a clean slate after any `TaskStop`.

### Bug — a schema gap that made a whole leak class undetectable
**What broke:** nothing crashed, but while writing the generator's test for `ISSUER_DOWNTIME` (a payment failure that overlaps an issuer/network outage), there was no field anywhere recording *when* a payment attempt actually happened.
**Why:** `PaymentAttempt` had every field from the PRD's original sketch except a timestamp — an oversight that's easy to miss until you try to answer "did this failure happen during the outage," which is the entire definition of that leak class.
**Fix:** added `attemptedAt` to `PaymentAttempt`, populated from the real payment's own timestamp during resolve (not `now()` at insert time — a delayed sweep shouldn't shift when the panel thinks the failure occurred).
**Learning:** the second schema gap caught this way (after `RawEvent.processedAt`). Both were found by trying to actually implement or test the behavior the field was needed for, not by re-reading the spec harder — worth remembering as the detectors and eval harness get built next.

### Bug — `.env.local` wasn't actually gitignored, despite looking like it should be
**What broke:** nothing yet — caught before it mattered. The root `.gitignore` had `.env` and `.env.*.local`, which reads like it should cover `.env.local`, but doesn't: `.env.*.local` requires *something* between `.env.` and `.local`, and `.env.local` has nothing there.
**Fix:** added `.env.local` as its own explicit line.
**Learning:** verified with `git check-ignore -v` rather than trusting the pattern by eye — it genuinely returned "not ignored" before the fix and "ignored" after. A plausible-looking glob pattern is still worth checking mechanically before relying on it to keep a secret out of git.

### Decision — server-to-server fetches only, so the frontend never needs CORS
Every real data fetch in `apps/web` runs in a Server Component or a Server Action — `lib/api.ts` is explicit that it's never meant to run in the browser. The one interactive piece (the ledger's "Verify chain" button) calls a Server Action, not `apps/api` directly, specifically so the browser never makes a cross-origin request to `localhost:8090` that `apps/api` doesn't set up CORS headers for. This was a deliberate choice, not an oversight discovered later — cheaper to decide once than to add CORS middleware and then have two ways to reach the same data.

### Decision — one hardcoded demo merchant, no login UI, matching the open question this was flagged as
Every screen renders `SEAM_DEMO_MERCHANT_ID` from the environment. This was flagged as an open question in the PRD (how much auth does the demo actually need) and resolved here in the simplest direction available: real session auth is real hours this build doesn't need to spend, and a hackathon demo showing one merchant's real data is a stronger showing than a login screen guarding an empty one.

### Bug — a third way to end up with a stale Prisma client, and a new trigger this time
**What broke:** every `apps/api` test file touching the database failed with `Cannot find module '.prisma/client/default'` immediately after scaffolding `apps/web` and running `pnpm install` at the workspace root — nothing about `apps/api`'s own schema or code had changed.
**Why:** Prisma's generated client lives inside a pnpm virtual-store path keyed by the resolved dependency graph (`node_modules/.pnpm/@prisma+client@.../node_modules/@prisma/client`). Adding a second workspace package with its own `@types/react`/`@types/react-dom` versions shifted that resolved graph enough to change the path, leaving the previously generated client orphaned at the old one.
**Fix:** `npx prisma generate` in `apps/api`, same fix as the first two times this category of bug showed up (schema push, then a schema field addition) — but the *trigger* this time was a sibling workspace package's dependencies changing, not anything in `apps/api` itself.
**Learning:** this is now a three-time pattern (see the earlier "Prisma client silently stale" entry) with three different triggers — a schema push, a mid-session schema edit, and now a workspace-level `pnpm install`. The safe habit going forward: run `prisma generate` after *any* root-level `pnpm install`, not just after touching `schema.prisma`.

### Bug — the generator's synthetic decline reasons didn't match the diagnosis lookup table at all
**What broke:** nothing crashed, but building the baselines eval revealed every `PAYMENT_BLOCKED` checkout the generator plants used the same hardcoded `errorReason: "payment_failed"`, which matches none of `classifyDiagnosis`'s patterns — every single one would silently classify as `UNKNOWN_TRANSIENT`, meaning Policy would never propose an action for any of them and the whole baselines eval would be measuring nothing.
**Fix:** the generator now picks from a varied, realistic set of reasons (`insufficient_funds`, `card_declined`, `authentication_failed`, `otp_verification_failed`, `suspected_fraud_risk`, plus one residual reason that deliberately stays unrecognised) — same discipline as leaving a genuine "unknown" tail in real data, not a suspiciously perfect distribution.

### Decision — widened the generator's minimum cart amount, and committed to reporting whatever the eval showed afterward
The generator's amounts were ₹300–5,000, an arbitrary choice from when it was first built. That range meant every synthetic leak cleared the ₹50 EV floor regardless of diagnosis, so the floor never had anything to reject and the "beats blast_everything" baseline comparison couldn't have shown a difference no matter what the policy did. Widened to ₹50–5,000 — real abandoned-cart amounts absolutely include small carts — and explicitly decided *before* re-running the eval not to touch this parameter again regardless of what the result looked like, specifically to keep the "committed before, not chosen after seeing results" discipline real rather than nominal.

### Finding — Seam ties or trails `blast_everything` on net value, and the honest reason is more useful than the number
Full writeup in `EVALUATION.md` and `LIMITATIONS.md`. The short version: every rupee of the gap traces to Shield correctly holding a specific action back (one for human approval, one below the profitability floor) that the naive baseline would have fired blindly — Seam's *total addressable value* (dispatched + pending) came within ~0.3% of blast's on the held-out run. The eval's own scenario design doesn't yet generate repeat customers hitting the contact cap, so that differentiator never gets to matter either. Reported as a real, quantified gap rather than reframed until it looked like a clean win — the alternative (tuning the eval until "beats" became true) would have defeated the entire point of pre-registering metrics before running anything.

### Decision — Seam's visual identity is the original "ledger" concept, not borrowed from anywhere
Early planning (when this was still assumed to extend the private reference system's codebase) called for adopting that system's actual shipped design system — a specific shadcn style, a specific brand color, a specific font. That's exactly the kind of connection this build has since deliberately cut. The fix wasn't to invent a new identity from nothing: a paper/ink ledger aesthetic — hairline rules, rupee figures as the visual hero, tabular-nums everywhere a number needs to line up — was the *original* creative direction from the very first pass at this project's design, before that got set aside in favor of reusing someone else's system. It was never derived from anywhere else, so reviving it as Seam's own identity is the honest choice, not a workaround. Palette: paper/ink neutrals with a copper accent (not the cliché warm-cream-plus-terracotta pairing — the base leans cool/bone, not cream). Type: Geist Sans + Geist Mono, both Vercel's own open fonts, chosen because Mono's tabular figures are functionally right for a ledger, not because of who else uses them.

### Learning — proving crash-resumability properly needed the right LangGraph primitive, not a forced simulation
The Block 1 proof faked a crash by throwing an error inside a node. That doesn't work for the real diagnosis graph, because its `classify` node deliberately catches every error from the model call (a malformed response is an expected outcome, not a crash — it's what triggers a retry). A first attempt at simulating a crash with an `AbortController` raced against the graph's own internal continuation and aborted a step too late. The actual right tool was `interruptAfter` at compile time — LangGraph's own mechanism for pausing a run right after a checkpoint commits, without throwing anything. That's not a lesser proof: a fresh process resuming a thread has no way to distinguish "the run was paused" from "the old process died" — the checkpoint on disk is identical either way, so proving resumption from an interrupt proves resumption from a crash.

### Decision — the injection fixtures prove the safety path, not detection quality
There's no OpenAI API key configured for this project, so nothing here can prove a live model actually recognizes every fixture in `injection-fixtures.ts` as an attack — that would need real credentials and is a model-quality question, not a code-correctness one. What's genuinely provable without a live model, and is proven directly: *if* a diagnosis comes back `PROMPT_INJECTION_SUSPECTED` — correctly detected or not — the system routes it through the identical path as `SUSPECTED_FRAUD`: escalated to a human, never auto-actioned, no exceptions. That's the claim that actually matters for safety, and it doesn't need a model call to verify.

### Decision — no real WhatsApp adapter for this build, and that's a change from the earlier plan
Early in this project's planning, a real WhatsApp Business Cloud API adapter looked reusable from the private reference system studied for precedent. That's no longer available — Seam is a standalone build with its own credentials, and it doesn't have a Meta Business app. Both SMS and WhatsApp are simulated executors behind one `ChannelAdapter` interface, exactly as the PRD's own "what we deliberately do not build" section already anticipated as the honest fallback. Swapping in a real adapter later is a one-file change, not a rearchitecture — the interface is already shaped for it.

### Decision — the idempotency reservation sits between Shield's stateless checks and dispatch, not inside evaluateShield itself
The PRD's Shield ordering names the reservation as check 6, between the daily-outreach cap and the content validator. `evaluateShield` stayed a pure function (no DB access, by design — see the Block 5 entry on why that mattered for testing). The reservation itself is real, impure, DB-touching work, so it lives in the executor, called right after Shield passes and right before any expensive work (a real Razorpay API call) happens — which is the actual intent behind "reserve before the LLM runs": lock in the idempotency guarantee before spending anything, not literally inline inside a stateless function.

### Bug — the detector was right, the ground truth was wrong
**What broke:** a checkout the generator labelled `PAYMENT_BLOCKED` in its ground truth got classified by the detector as `ISSUER_DOWNTIME` instead — looked at first like a detector bug.
**Why:** the generator picks a random payment method and a random time-of-day independently for every checkout, including `PAYMENT_BLOCKED` ones. By chance, one landed on the same method and time window as the synthetic downtime outage — which, by the actual rule ("`ISSUER_DOWNTIME` is a `PAYMENT_BLOCKED` that overlaps an active downtime window"), *is* an issuer-downtime case. The detector was correct; the generator's label was the bug.
**Fix:** `PAYMENT_BLOCKED` and clean checkouts now pick their payment method from the set that excludes the downtime window's method, so the two scenarios can never accidentally collide.
**Learning:** when a test fails, check which side is actually wrong before "fixing" the code that produced the surprising answer — the detector's own unit tests (written first, independent of the generator) already proved its downtime-overlap logic was correct in isolation, which is what made it obvious the generator was the thing to fix, not the detector.

### Decision — a CHECK constraint as a second line of defense, not a replacement for the tested one
`classifyCheckout` is already proven to never return a leak with empty evidence, and `detect-for-merchant.test.ts` proves it again through the full write path. A `CHECK (cardinality(evidenceEventIds) > 0)` constraint on the `Leak` table on top of that isn't redundant — it protects against a *different* future bug (some other write path to the same table that doesn't go through this code). Prisma 7 can't express CHECK constraints in `schema.prisma`, so it lives in `prisma/manual-constraints.sql` and has to be applied by hand once per fresh database — documented in `AGENTS.md` so it isn't just tribal knowledge.

### Decision — the ledger is one global chain, locked with a Postgres advisory lock
**What:** the hash chain isn't per-merchant — every merchant's entries interleave in one linear sequence, and screen 3's "filter by merchant" is a display concern, not a chain-structure one.
**Why it needs a lock at all:** two concurrent appends both reading "the last entry" under Postgres's default isolation can both build on the same `prevHash`, forking the chain — a `SELECT ... FOR UPDATE` on the last row doesn't help either, because there's nothing to lock yet before the very first entry exists.
**Fix:** `pg_advisory_xact_lock` on a fixed key, held for the transaction's duration — serializes every append, including the genesis case. Proven with a real test: 10 concurrent `appendLedgerEntry` calls, then `verifyLedgerChain()` confirms one straight, unbroken line, not a fork.

### Bug — a tampered-chain response that would have crashed on the exact request that needed it most
**What broke:** `GET /ledger/verify` on a genuinely broken chain threw `TypeError: Do not know how to serialize a BigInt` instead of returning the 409 it was supposed to.
**Why:** `brokenAtSeq` is a Postgres `bigserial`, which Prisma maps to a JS `bigint` — and `JSON.stringify` (which Hono's `c.json()` uses) throws on a bare `bigint` rather than silently stringifying it.
**Fix:** convert `brokenAtSeq` to a string before it crosses the JSON boundary, same as every other bigint field already leaving this API.
**Learning:** confirmed this was a real bug, not defensive coding for something that couldn't happen — reverted the fix, watched the exact predicted crash happen, then restored it. The failure mode is exactly the demo-day nightmare: the one code path that only runs when something's actually wrong (a tampered chain) is also the one path least likely to get exercised by casual manual testing.

### Learning — proving "fails closed" took a deliberate choice of API, not just a try/catch
**What:** Shield's content check originally used `/pattern/.test(text)`, which coerces its argument to a string — so a `null` message would silently become the string `"null"`, match nothing, and pass every check instead of throwing. That would have made the "fails closed" test pass for the wrong reason (nothing ever actually failed).
**Fix:** switched to `text.match(pattern)`, which throws a real `TypeError` on `null`/`undefined` — so the fail-closed wrapper's `catch` block is genuinely exercised, not just present in the code.
**Learning:** "fails closed" is a claim about what happens when something throws — proving it means finding an input that *actually* throws, not just wrapping code in try/catch and trusting it. `.test()` vs `.match()` was the difference between a real proof and a test that would pass even if the catch block were deleted.

### Decision — the generator covers four of six leak classes, on purpose
`PAYMENT_BLOCKED`, `ISSUER_DOWNTIME`, `SILENT_ABANDON`, and `PRE_CHECKOUT_DROP` are all expressible with today's schema and are built and tested. `METHOD_CONCENTRATION` needs a 14-day baseline (one merchant-day of data can't establish a baseline to deviate from) and `POST_PURCHASE_LEAK` needs a refund/return model that doesn't exist yet — building either now would mean guessing at a shape before the detector that consumes it exists. Deferred deliberately, not forgotten.

### Naming — renamed twice before settling
The project went through two names before landing on **Seam**, which is also the central metaphor: two systems (storefront, payment gateway) that don't share a customer identity have a seam between them, and that seam is exactly where revenue goes missing unaccounted for. Renaming a running codebase is mechanical but easy to do sloppily — a global find-and-replace on macOS's `sed` missed one lowercase instance because BSD `sed`'s word-boundary matching isn't identical to GNU `sed`'s. Caught by grepping for the old name again after the rename, not by trusting the first pass.

### Decision — real auth, and three on-thesis features adapted from causal-ai instead of ported
Once login existed, "market intelligence / support tickets / weekly digest" from causal-ai got rebuilt as Seam-native equivalents rather than literal ports, because the originals depend on credentials this project doesn't have (Gmail, WhatsApp inbox, web search): **Leak intelligence** (`src/intelligence/`) reuses the already-deferred `METHOD_CONCENTRATION` z-score detector — the earlier "four of six leak classes, on purpose" note above is now superseded; the 14-day baseline concern turned out to be satisfiable with `MIN_BASELINE_DAYS = 7` once a real multi-day generator existed. **Recovery conversation handling** (`src/replies/`) reframes "support tickets" as reply classification against Seam's own recovery messages — PROMISE/DONE need no human, REFUSE/UNCLEAR/OPTOUT open a `Ticket`, and OPTOUT additionally writes to a new `OptOut` table. **Weekly digest** (`src/digest/`) is a templated founder brief built fresh from Seam's own Leak/RecoveryAction rows, explicitly labeled "predicted" wherever it cites EV rather than realised revenue (LIMITATIONS.md §2 — no outcome worker exists yet).

### Decision — Shield looks up opt-out itself; the caller can no longer assert it
**What:** `executeAction`'s `shieldContext` used to take a caller-supplied `optedOut: boolean`. Once real inbound replies could produce a real `OptOut` row, that shape became a trap — a caller that forgot to look the flag up first would silently bypass the block. Removed the field entirely; `executeAction` now calls `isOptedOut(merchantId, customerPhone)` against the database itself before building Shield's input.
**Why:** an opt-out check that depends on every call site remembering to pass the right boolean isn't really a guarantee — it's a convention that will eventually get forgotten under deadline pressure. Making the lookup unconditional and internal closes the loop for real: a customer's actual "STOP" reply (`handle-reply.ts` → `OptOut` upsert) now blocks every future contact attempt, not just ones where the caller happened to check first.
**Fix required updating the existing test too:** `execute-action.test.ts`'s "opted-out customer" case previously injected `shieldContext: { optedOut: true }` directly; rewritten to seed a real `prisma.optOut.create(...)` row for the test's own phone number before calling `executeAction`, so the test now proves the real lookup path, not a bypassed one.

### Bug — a lingering singular/plural bug in the digest narrative, caught while wiring the frontend
**What broke:** `buildDigestNarrative` said "Shield blocked 1 actions" for a merchant with exactly one blocked action — noticed live, reading the actual rendered digest page against the seeded demo merchant's real data, not from a written test.
**Why:** the file already had the same singular/plural guard for "recovery message(s)" and "leak(s)" a few lines above — this one spot was just missed the first time.
**Fix:** same pattern applied — `actionsBlocked === 1 ? "action" : "actions"` — plus a regression test (`build-narrative.test.ts`) pinning the singular case, so a live read caught something the existing test suite hadn't.
**Learning:** typechecking and the existing suite both stayed green through this whole bug's lifetime — it only surfaced by actually looking at rendered output against real seeded data, which is why AGENTS.md's "verify live before reporting done" rule exists.

### Frontend — three new authenticated pages, wired against real endpoints, no mock data
Built `/recovery/intelligence` (Leak intelligence findings + an on-demand "run analysis" button), `/recovery/tickets` (open conversations needing a human + a form that simulates an inbound reply, since there's no real SMS/WhatsApp inbound webhook — see the WhatsApp-adapter decision above), and `/recovery/digest` (the founder brief). All three were checked against the live dev servers with the seeded demo merchant (`founder@kolamandco.example`) using a real session cookie, not just `tsc --noEmit` — confirmed real rendered content (the actual narrative text, an actual "STOP messaging me" ticket, actual stat numbers) rather than an empty-state or error boundary silently swallowing a broken fetch.

### Decision — closed the disclosed API auth gap: `apps/api`'s merchant routes now verify the session, not just the URL
**What:** every `/merchants/:id/...` route (`leaks`, `recovery-actions`, `digest`, `tickets`, `intelligence/analyze`, `razorpay/connect`) sits behind `src/auth/middleware.ts`'s `requireOwnMerchant` — it verifies the caller's JWT and 403s if the session's own `merchantId` doesn't match the `:id` in the URL. `POST /recovery-actions/:id/reply` uses the lighter `requireSession` instead and now derives `merchantId` from the verified session rather than trusting it in the request body — a caller-supplied `merchantId` there is silently dropped by Zod (the field was removed from the schema entirely, not just ignored at the call site).
**Why now, not from the start:** this was disclosed as a known gap in `LIMITATIONS.md` §6 since auth was first added, deferred deliberately rather than half-done under time pressure — closing it needed a real HTTP-level test proving the exact vulnerability (a valid session for merchant A reading merchant B's data) rather than just adding the check and hoping.
**A real TypeScript gotcha along the way:** once `requireOwnMerchant` (typed against a generic, path-unaware `Context`) sat in front of a handler, `c.req.param("id")` widened from the route-literal-inferred `string` to `string | undefined` throughout that handler — Hono's route-param typing comes from the string literal passed to `.get()`/`.post()`, and a generic middleware in the chain loses that specificity for TypeScript's inference, even though nothing changes at runtime. Fixed by typing every affected `Hono` app as `Hono<AuthEnv>` (a shared `{ Variables: { merchantId: string } }` type exported from `middleware.ts`) and having handlers read `c.get("merchantId")` — the middleware-verified value — instead of re-reading `c.req.param("id")`, which is more correct anyway: it's what was actually checked, not what merely appears in the URL.
**Proof, not just typecheck:** every `*/routes.test.ts` file now has 401 (no session) and 403 (someone else's session) cases alongside the existing 200 case, generating real JWTs with `generateToken` the same way `/auth/login` does, hitting the actual Hono app via `.request()` — confirmed live against a real running server too (`curl` with no token, a stranger's token, and the real token, getting 401/403/200 respectively) before calling this done.
**Frontend side:** `apps/web/lib/api.ts` now forwards the same `auth-token` httpOnly cookie as an `Authorization: Bearer` header on every server-to-server fetch to `apps/api` — one change, in one file, rather than threading a token through every page component, since every caller of `lib/api.ts`'s functions already runs in a Server Component or Server Action where `next/headers`'s `cookies()` is available directly.
**Scoping decision, disclosed rather than silently assumed:** `GET /ledger` and `GET /ledger/verify` were deliberately left outside this boundary — the ledger is one global, publicly-verifiable hash chain by design (see the ledger decision above), and the PRD's own submission video script calls for verifying it live, which argues against gating it behind login.

### Real credentials arrive — Groq and OpenRouter replace the "no OPENAI_API_KEY" gap for real, live testing
**What:** given a real Groq key and a real OpenRouter key, `src/llm/providers.ts` was added as the single place both LLM-touching paths get their model from: `diagnosisModel()` (Groq) for the 4s-budget, structured-JSON diagnosis classification, `chatModel()` (OpenRouter) for the multi-turn, tool-calling chat agent. **A genuine upstream schema-serialization bug, found by actually running the thing live — not by code review.** The first live diagnosis run against Groq failed with `additionalProperties '$schema', 'properties'... not allowed` — Groq's strict JSON-schema validator rejecting a schema that `ai`'s zod-to-JSON-Schema conversion had corrupted (a zod-v4-internal `~standard` key leaking into the JSON Schema sent over the wire), and the model, faced with an impossible schema, sometimes echoed schema-shaped keys back into its own answer instead of just answering the question. **What:** on the explicit ask "how do I run Shield/Recovery/Executor/Conversation/Diagnosis, fix that," built three new agent modules (`diagnosis-agent.ts`, `recovery-executor.ts`, `shield-recheck.ts`), wired each to a live `POST /merchants/:id/agents/<id>/run` route, widened the frontend's `TriggerableAgentId` union and `RunNowButton`, and added a fleet-page "Run all agents" button (`fleet-actions.ts`) that sweeps detector → diagnosis → recovery → shield → intelligence → opportunities in dependency order. Conversations and Store Chat, being event-driven rather than sweep-style, got an "Open conversations" / "Open chat" link on their detail pages instead of a batch trigger — a real answer to "how do I run this one," just not a run button, because there's nothing to batch.

**A genuinely undiscovered gap, found while building the Diagnosis Agent: the `Diagnosis` table had always been empty.** Nothing in the running app, before this pass, ever wrote to `prisma.diagnosis` — it was only ever `count()`-ed (always 0, silently) by the fleet page's activity metric. `opportunities.ts` computed a diagnosis inline via `classifyDiagnosis` every time and threw the result away rather than persisting it. `diagnosis-agent.ts` is the fix: it persists a real row per leak, deterministic pattern-matching first, escalating to the live Groq model (from the same-session's provider work) only when rules can't resolve it — closing LIMITATIONS.md §4/§10 in the more substantial sense of "actually produces a durable, auditable record," not just "has been called."

**Recovery Executor reuses a persisted Diagnosis when one exists, falls back to computing it inline when one doesn't** — order-independent by design, so "run diagnosis then recovery" is the complete flow but "run recovery" alone still works standalone, same as `opportunities.ts` always could. It calls the exact same `reserveAction()` used by the real dispatch path (`execute-action.ts`) for the RESERVED case, and for a Shield-blocked leak, reserves then immediately marks it `FAILED` — the identical two-step pattern `execute-action.ts` itself already uses when a later step fails, not a new convention invented for this agent.

**Shield's own "run" had no obvious honest shape, and the dishonest shape was tempting.** A full re-run of Shield's seven checks needs a customer contact history `RecoveryAction` doesn't retain (LIMITATIONS.md §13's schema gap, again) — so a "full recheck" button would have had to either fake the missing inputs as passing (silently weaker than it looks) or crash. Neither was acceptable. `shield-recheck.ts` instead re-runs only the two checks that don't need that missing data (quiet hours, EV floor) against currently-live inputs, and says so in its own file comment — a real, narrower thing, disclosed as narrower, rather than a fake wide thing.

### The synthetic dataset now runs through the real pipeline, not a hand-typed fixture
**What:** `scripts/seed-demo.ts` was rewritten from "generate one day of data, hand-insert two `RecoveryAction` rows" to "generate a richer dataset, then run the actual live agent functions over it" — the same `runDiagnosisAgent`/`runRecoveryExecutor`/`runShieldRecheck`/`analyzeLeakIntelligence` the fleet's own buttons call, each wrapped in the real `recordAgentRun` harness so a fresh demo login shows real run history immediately, not data with no audit trail behind it. Re-running the script now resets the prior demo merchant and every row scoped to it first, rather than accumulating duplicates.

**Two leaks are hand-guaranteed, and why that's not the same as faking the outcome.** Whether the generator's random decline-reason draw happens to include `payment_failed` (the one reason `classifyDiagnosis` can't resolve) is down to RNG luck for a given seed — a first run genuinely came back "1 llm" only because `payment_failed` happened to be drawn; a second, otherwise-identical-looking change could just as easily produce 0. Rather than leave the live-LLM path's demoability to chance, one leak with that exact reason is inserted directly. Same reasoning for a guaranteed Shield-blocked example: the amount has to clear `decide()`'s own EV floor while staying under Shield's separate, lower amount floor — a window that only exists for a high-recovery-rate diagnosis class (ISSUER_DOWNTIME, 0.35), worked out by hand from the actual formulas in `decide.ts` and `evaluate.ts`, not guessed. Both leaks still flow through the identical real `classifyDiagnosis` → `decide()` → `evaluateShield()` → `reserveAction()` code every generated leak does — only their existence is guaranteed, not their outcome.

**A real bug found by the numbers not reproducing between two identical-looking runs.** Reseeding twice in a row with the exact same seeded generator produced different reserved/blocked counts — surprising, since every RNG call in `generate-merchant-day.ts` is seeded and deterministic. Root cause: `DowntimeWindow` has no `merchantId` (it's implicitly global, issuer-wide data, per that model's own design) and the seed script's reset step only ever deleted rows scoped to the demo merchant — so each reseed left behind one more stale `upi` downtime window from a previous run, each anchored to a different real timestamp. Which one `.find()` picked first (an unspecified row order without an `ORDER BY`) changed how the ISSUER_DOWNTIME leaks the detector produced got classified downstream, which changed the final reserved/blocked mix. Fixed by clearing `DowntimeWindow` entirely at the start of every reseed — safe here specifically because this dev database only ever holds the one demo merchant; a shared multi-merchant environment would need a real per-merchant or per-run scoping mechanism instead.

**Quiet hours is real, and a demo shouldn't be at its mercy.** Shield's quiet-hours check depends on the actual wall-clock time, correctly — a live "Run all agents" click at 2am IST should genuinely see everything deferred, that's the feature working. But `seed-demo.ts`'s job is producing a stable, demoable dataset regardless of when it happens to run, so its own executor/Shield-recheck calls are pinned to a fixed daytime IST hour on today's date, disclosed in the script's own comment as specific to seeding, not a change to how a live request is evaluated.
